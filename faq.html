Étape 0 · Prérequis & environnements

Mise en place

Pourquoi deux environnements (CloudShell vs poste local) ?

CloudShell est authentifié sur la sandbox AWS : tout ce qui touche AWS/le cluster s'y fait, sans risque pour un compte d'entreprise. Le poste local ne sert qu'à écrire le chart et faire du git — jamais de commande AWS en local.

Je n'ai pas de compte AWS perso, c'est grave ?

Non. L'accès AWS est fourni par la sandbox Pluralsight (compte cloud_user, éphémère). Aucun compte perso ni carte bancaire requis.

Pourquoi installer eksctl mais pas aws/kubectl/git ?

CloudShell fournit déjà aws, kubectl et git. Seul eksctl (création du cluster EKS) manque et s'installe en une commande.

C'est quoi « Safe Paste » dans CloudShell ?

Une confirmation de sécurité quand on colle plusieurs lignes d'un coup : cliquer sur Paste. Sans ça, le collage multi-lignes (heredoc notamment) peut être tronqué.

Étape 1 · Créer le cluster EKS

Création du cluster

Pourquoi ça prend 15-20 minutes ?

eksctl crée le cluster via CloudFormation : d'abord le control plane (géré par AWS) + le réseau, puis les nœuds EC2. Ces provisionnements AWS sont longs par nature. On lance la création tôt et on enchaîne sur la théorie pendant ce temps.

C'est quoi un « managed node group » ?

Un groupe de nœuds (ici 2 × t3.medium) dont AWS gère le cycle de vie (création, mises à jour, remplacement). On déclare juste le type et le nombre ; AWS s'occupe du reste.

L'avertissement « Auto Mode will be enabled… », je dois faire quelque chose ?

Non. C'est une notice sur un comportement futur d'eksctl. Aujourd'hui, le mode classique (nœuds managés qu'on contrôle) s'applique — exactement ce qu'on veut.

Si CloudShell se déconnecte pendant la création ?

Pas de panique : la création continue côté AWS (CloudFormation). On rouvre CloudShell, on recolle le cluster.yaml puis on reconfigure kubectl avec aws eks update-kubeconfig.

Pourquoi EKS 1.34 ? Et si eksctl la refuse ?

La sandbox n'autorise que les versions en « standard support ». 1.34 l'est actuellement. Si un jour eksctl la refuse, il affiche les versions valides du jour — on en reprend une (ex. 1.35).

Étapes 2-3 · Théorie & vérification

Concepts & contrôle du cluster

En une phrase : Kubernetes, GitOps, Helm ?

Kubernetes orchestre des conteneurs à partir d'un état décrit en YAML. GitOps fait de Git la source de vérité (un agent réaligne le cluster sur le dépôt). Helm est le gestionnaire de paquets : des manifests templatés paramétrés par des valeurs.

Où tournent les addons (vpc-cni, kube-proxy, coredns, metrics-server) ?

Sur nos nœuds (le seul node group ng-atelier). vpc-cni et kube-proxy sont des DaemonSets (un pod par nœud) ; coredns et metrics-server sont des Deployments posés par le scheduler. Le control plane, lui, est géré par AWS, hors de nos nœuds.

« 2 nœuds Ready » : c'est quoi un nœud, au juste ?

Une machine (ici une instance EC2 t3.medium) qui exécute les pods. Ready = le nœud a rejoint le cluster et peut accueillir des charges. On en a 2 pour la résilience.

Étape 4 · Installer ArgoCD

ArgoCD

C'est quoi ArgoCD, concrètement ?

Un agent qui tourne dans le cluster et compare en continu l'état réel avec ce qui est décrit dans un dépôt Git. En cas d'écart, il réaligne le cluster. On ne fait plus kubectl apply à la main : on commite, ArgoCD applique.

Pourquoi --server-side --force-conflicts à l'installation ?

Le manifest ArgoCD contient de grosses CRDs. L'apply « server-side » évite l'erreur « annotation too long » du mode client-side ; --force-conflicts tranche les conflits de propriété de champ en faveur de notre apply.

Que fait kubectl wait … condition=available ?

Il bloque jusqu'à ce que le déploiement argocd-server ait assez de pods prêts (ou timeout 300s). condition met = c'est prêt, on peut continuer.

ArgoCD est installé mais je ne vois pas d'interface. Normal ?

Oui. L'UI existe (service argocd-server) mais n'est pas exposée. On y accède à l'étape 5 via un port-forward local (CloudShell ne peut pas ouvrir de port web).

ArgoCD = Argo Workflows ?

Non. Même famille (projet Argo) mais outils différents : ArgoCD = déploiement continu/GitOps ; Argo Workflows = moteur de pipelines/jobs.

Étape 5 · Accès aux UIs (kubeconfig)

Kubeconfig par jeton & UI ArgoCD

Pourquoi un kubeconfig par jeton au lieu d'aws eks update-kubeconfig ?

Pour respecter la règle « jamais de commande AWS en local ». Le kubeconfig par jeton s'authentifie avec un token Kubernetes (pas des identifiants AWS), donc on peut l'utiliser depuis le poste local sans jamais appeler AWS.

Pourquoi passer par un port-forward et pas une URL publique ?

CloudShell ne peut pas ouvrir de port web, et on ne veut pas exposer ArgoCD sur internet. Le port-forward crée un tunnel local sécurisé (localhost:8080 → service dans le cluster) — simple et sans config réseau.

Le navigateur affiche « certificat non sécurisé », c'est grave ?

Non. ArgoCD utilise un certificat auto-signé interne. En local, via le tunnel, c'est attendu : on accepte l'avertissement.

Où est le mot de passe admin d'ArgoCD ?

L'utilisateur est toujours admin. Le mot de passe est généré automatiquement et stocké dans le secret argocd-initial-admin-secret (on le décode en base64). On le récupère une fois, on le note.

Le token du kubeconfig expire quand ?

Au bout de 24h (durée fixée à sa création). Au-delà, il faut régénérer le kubeconfig dans CloudShell. De toute façon la sandbox ne vit que ~4h.

export KUBECONFIG va-t-il casser mon kubectl habituel ?

Non. export KUBECONFIG=… ne vaut que pour le terminal courant et n'écrase pas ~/.kube/config. Il faut le refaire dans chaque nouveau terminal (ex. celui du port-forward et celui des commandes).

L'UI ArgoCD est vide, je n'ai rien raté ?

Non, c'est normal : aucune Application n'est encore déclarée. On en crée une à l'étape 6, elle apparaîtra alors dans l'UI.

Tous ces pods ArgoCD (kubectl get all -n argocd), à quoi servent-ils ?

Les 3 essentiels pour l'atelier :

• application-controller — le cerveau : compare en boucle Git ↔ cluster et applique les écarts (la réconciliation GitOps). C'est un StatefulSet (nom en -0).
• repo-server — clone le dépôt Git et rend le chart (helm template). Les erreurs de chart apparaissent ici.
• server — l'API + l'UI web (celle du port-forward 8080).

Le support : redis = cache (accélère l'UI, pas de données critiques).

Présents par défaut mais non utilisés dans l'atelier : applicationset-controller (génère des Applications en masse), dex-server (SSO externe — ici on utilise le compte local admin), notifications-controller (Slack/email).

Mécanique K8s en dessous : chaque composant est un Deployment (ou StatefulSet pour le controller) → qui crée un ReplicaSet → qui crée le Pod. Les Services en -metrics exposent juste les métriques Prometheus de chaque composant.

Étape 6 · Fork & Application ArgoCD

Déclarer l'application

C'est quoi une « Application » ArgoCD ?

Un objet Kubernetes (CRD) qui dit à ArgoCD : « surveille ce dépôt Git, à ce chemin, et synchronise-le dans ce namespace ». Ici elle pointe vers charts/podinfo de votre fork et déploie dans le namespace podinfo.

Pourquoi remplacer repoURL par l'URL de MON fork ?

Parce qu'ArgoCD va suivre votre dépôt : c'est là que vous committerez vos templates. S'il pointait vers le dépôt d'origine, vos commits ne seraient pas pris en compte.

L'app est Synced/Healthy mais rien n'est déployé. Normal ?

Oui, si templates/ est vide : Helm ne rend aucun manifest, donc ArgoCD n'a rien à appliquer — mais l'app est bien « synchronisée » avec un dépôt… vide. Le namespace podinfo sera créé au premier template.

Synced vs Healthy, quelle différence ?

Synced = l'état du cluster correspond à Git. Healthy = les ressources déployées fonctionnent (pods Running, etc.). Une app peut être Synced mais Degraded (un pod qui crashe), ou OutOfSync mais Healthy (un changement committé pas encore appliqué).

CreateNamespace=true, à quoi ça sert ?

C'est une option de sync qui dit à ArgoCD de créer automatiquement le namespace cible (podinfo) s'il n'existe pas. Sans elle, il faudrait le créer à la main.

Étape 7 · Construire le chart pas à pas

Écrire les templates (le cœur du TP)

helm lint vs helm template ?

lint vérifie la structure du chart (syntaxe, valeurs manquantes). template affiche le YAML final (valeurs substituées) — pratique pour vérifier qu'il ne reste aucun {{ }} non résolu avant de committer.

Je commite, mais le cluster ne change pas tout de suite ?

ArgoCD scrute le dépôt périodiquement (quelques minutes) ou via webhook. On peut forcer depuis l'UI (bouton Refresh / Sync). Le délai est normal.

Pourquoi des requests CPU dès le Deployment (7.1) ?

Parce que le HPA (7.5) calcule un pourcentage d'utilisation CPU par rapport à la requête. Sans requests.cpu, le HPA ne peut rien calculer et reste inopérant.

Comment podinfo lit PODINFO_UI_MESSAGE / _COLOR ?

podinfo est une 12-factor app : chaque option se pilote par variable d'environnement PODINFO_<SECTION>_<CLE>. Helm injecte ces variables depuis values.yaml — changer la valeur et committer suffit à mettre à jour l'UI.

À quoi servent les sondes liveness et readiness ?

liveness (/healthz) : si elle échoue, K8s redémarre le conteneur. readiness (/readyz) : si elle échoue, K8s retire le pod du Service (plus de trafic) sans le tuer. Deux rôles complémentaires.

Le HPA reste à 1 pod, il ne marche pas ?

Si. Au repos, le CPU est très bas (ex. cpu: 2%/50%), donc le HPA garde le minimum (1 pod). Il ne scale que si la charge dépasse la cible. C'est le comportement attendu.

Pourquoi autoscaling/v2 et pas v1 ?

La v2 permet plusieurs métriques et la forme Resource → cpu → Utilization. La v1 est limitée au seul CPU avec un champ dédié. La v2 est la version stable et recommandée.

Étape 8.1 · Kubernetes Dashboard

UI de supervision du cluster

Faut-il déployer metrics-server ?

Non. L'eksctl de l'atelier l'installe comme addon EKS par défaut à la création du cluster. On s'appuie dessus — en déployer un second ferait doublon sur l'API metrics.k8s.io. On le vérifie avec kubectl top nodes.

Pourquoi le port 8443 et le service kong-proxy ?

Le Dashboard v7 s'expose en HTTPS via un proxy Kong sur le port 443. Le port-forward 8443:443 relie localhost:8443 à ce proxy.

D'où vient le token de connexion au Dashboard ?

On crée un ServiceAccount dashboard-admin + un ClusterRoleBinding, puis kubectl create token génère un jeton éphémère (~1h) à coller dans l'UI. Un nouveau token se régénère avec la même commande.

Les graphiques CPU/RAM sont vides au début, c'est grave ?

Non : le metrics-server collecte toutes les ~15 s. Attendez ~1 min après l'ouverture pour voir les courbes se remplir. Si rien n'apparaît durablement, vérifiez kubectl top nodes.

cluster-admin pour le Dashboard, c'est risqué ?

Oui en production. Ici c'est assumé (sandbox jetable) pour simplifier. Sur un vrai cluster, on créerait un rôle restreint (lecture seule, namespace ciblé) au lieu de cluster-admin.

Étape 8.2 · Prometheus (kube-prometheus-stack)

Collecte des métriques

Prometheus et metrics-server, ce n'est pas la même chose ?

Non. metrics-server fournit des métriques instantanées (CPU/RAM) pour kubectl top et le HPA. Prometheus est un vrai système de monitoring : il stocke des séries temporelles, permet des requêtes (PromQL), des graphiques et des alertes.

Pourquoi « profil allégé » ? Qu'a-t-on désactivé ?

Pour tenir sur la sandbox : pas d'Alertmanager, pas de Grafana, une seule réplique Prometheus, rétention courte, pas de stockage persistant. On garde l'essentiel : operator, Prometheus, node-exporter, kube-state-metrics.

La 1ʳᵉ synchro passe par OutOfSync / Progressing, c'est un bug ?

Non. Le chart installe de grosses CRDs puis plusieurs composants ; ArgoCD affiche des états transitoires le temps que tout se stabilise. L'option ServerSideApply=true évite l'erreur « annotation too long » liée aux CRDs.

C'est quoi node-exporter et kube-state-metrics ?

node-exporter = métriques de l'OS de chaque nœud (CPU, mémoire, disque, réseau) via un DaemonSet. kube-state-metrics = état des objets Kubernetes (nombre de pods, deployments prêts, etc.). Les deux sont scrapés par Prometheus.

Est-ce que ça tient sur 2 nœuds t3.medium ?

Oui, avec le profil allégé. Après installation, les nœuds restent sous ~50 % de RAM. Un pic CPU transitoire au démarrage de Prometheus (ingestion initiale) est normal et redescend.

Étape 8.3 · ServiceMonitor (podinfo scrapé)

Relier podinfo à Prometheus

C'est quoi un ServiceMonitor ?

Une CRD installée par l'operator Prometheus. Elle décrit quel Service scraper (via un selector de labels) et sur quel endpoint (port: http, path: /metrics). Prometheus la détecte et se met à collecter automatiquement — tout en déclaratif, en GitOps.

Pourquoi un {{- if .Values.serviceMonitor.enabled }} ?

Pour rendre le template optionnel : si la CRD ServiceMonitor n'existe pas (Prometheus pas installé), on peut désactiver le rendu via values.yaml et éviter une erreur. Même logique que le garde du HPA.

Comment vérifier que Prometheus scrape bien podinfo ?

Dans l'UI Prometheus (port-forward 9090) : Status → Targets → la cible podinfo doit être UP. Ou en PromQL : up{namespace="podinfo"} doit renvoyer 1.

La cible n'apparaît pas / est DOWN, que vérifier ?

1) Les labels du selector.matchLabels du ServiceMonitor correspondent-ils à ceux du Service podinfo (app: podinfo) ? 2) Le port est-il référencé par son nom (http) ? 3) Laissez 30-60 s à Prometheus pour découvrir le ServiceMonitor.

Pourquoi podinfo expose-t-il déjà /metrics ?

podinfo embarque un endpoint Prometheus natif sur /metrics (port 9898). On n'ajoute donc pas de code applicatif : on déclare juste le ServiceMonitor pour que Prometheus vienne le lire.
